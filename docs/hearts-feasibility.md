# Hearts & Lives feasibility

Reviewed 18 November 2026. This is a documentation and API review. Minecraft runtime tests, including PS5 tests, are pending.

## Decision

The exact design is **blocked for a supported stable release**. Bedrock exposes the player's current health and hunger, but the stable creator API has no documented way to lower either native maximum per player. It also exposes no API to set the number of native heart or hunger slots. A scripted limit can approximate a cap, and a separate display can report that limit. Neither demonstrates the required native caps or HUD. Hunger clamping also interacts with the game's feeding, healing and sprint rules.

Stable APIs cover the building blocks for independent lives, death and respawn, spectator elimination, shaped crafting and scripted recovery. Their reliability still needs a runtime prototype. Windows hosting and Bedrock cross-platform play are documented. The specific route of a PS5 joining a Windows friend world with a privately distributed scripted add-on remains a hardware test gate.

## Supported version baseline

- Use retail Bedrock **26.60** as the initial target. Mojang's production samples are tagged **`v1.26.60.5`**. Record the installed Windows and PS5 build numbers independently. Use behavior and resource pack manifest format **2**, proposed `min_engine_version` **`[1, 26, 60]`**, a `script` module in the behavior pack, and **`@minecraft/server` `2.11.0`** in its dependencies. Verify that exact combination in retail because a package listing and sample release do not prove in-game load. [Mojang retail samples][retail] · [Pack manifest][manifest] · [Script module reference][server] · [Published 2.11.0 declarations][types]
- The stable `2.0.0` line shipped in Bedrock `1.21.90`. In the module changelog, health and death event surfaces are present by `1.4.0`, world and entity dynamic properties were added in `1.7.0`, HUD visibility and per-player game modes in `1.11.0`, hunger/saturation/exhaustion and custom commands in `2.1.0`, and cancellable heal/hurt events in `2.6.0`. These are API milestones. The prototype supports the retail target above and makes no older-build compatibility claim. Use stable declarations to check individual members because the generated reference also contains experimental entries. [1.21.90 creator release notes][v190] · [API changelog][changelog] · [Stable and beta tracks][versioning]

## 1. Maximum health and the native HUD

- **Documented.** `player.getComponent(EntityComponentTypes.Health)` (`minecraft:health`) returns `EntityHealthComponent`. Its inherited `currentValue`, `effectiveMax` and `effectiveMin` are read-only. `setCurrentValue(value: number): boolean` changes current health and can throw for an out-of-bounds value. One health point is half a heart. `player.onScreenDisplay.setHudVisibility(HudVisibility.Hide, [HudElement.Health])` and `HudVisibility.Reset` control visibility. `setActionBar(...)` displays text separately. [Health component][health] · [Attribute API][attr] · [Health point units][healthjson] · [ScreenDisplay][screen] · [HudElement][hud]
- **Unsupported as a stable contract.** There is no documented player max-health setter or native slot-count setter. Generic `minecraft:health` JSON supports `value` and `max` for entities. The retail player definition omits that component. Applying a component group to a replacement `minecraft:player` definition is an unproven engine test, with whole-player pack conflicts and update risk. `Entity.addEffect(...)` with `health_boost` is an effect-based increase, with no documented reduction below vanilla. Absorption adds a separate buffer. [Entity JSON reference][healthjson] · [Retail player definition][playerjson] · [Entity API][entity] · [Effect list][effect]
- **Workaround.** Store a per-player health limit and test bounding `EntityHealBeforeEvent.healing` through `world.beforeEvents.entityHeal`, correcting observed changes through `world.afterEvents.entityHealthChanged`, and reconciling on spawn. A tick clamp alone can allow over-cap health to affect damage before the next correction. Validate event coverage and ordering with natural healing, potions, absorption and Totems of Undying. The vanilla HUD can still show empty slots for the base maximum. A numeric action bar is feasible as a separate display. An RP HUD replacement has client, layout and pack-stack risk, and cannot itself change the engine maximum. [World before events][before] · [World after events][after] · [ScreenDisplay][screen] · [Retail HUD definition][hudjson]

## 2. Maximum hunger, HUD and sprint

- **Documented.** `player.getComponent(EntityComponentTypes.Hunger)` (`minecraft:player.hunger`) returns `EntityHungerComponent`, with the same read-only `effectiveMax` and writable current value via `setCurrentValue(...)`. `EntityComponentTypes.Saturation` and `Exhaustion` expose separate attributes. `HudElement.Hunger` controls bar visibility. `Entity.isSprinting` reports sprint state and is read-only. `PlayerInputPermissions.setPermissionCategory(...)` has movement categories without a sprint-specific permission. [Hunger component][hunger] · [Component types][components] · [Attribute API][attr] · [Entity API][entity] · [Input categories][input] · [HudElement][hud]
- **Unsupported as a stable contract.** The reviewed APIs expose no hunger-cap setter, native hunger slot-count setter, or sprint-threshold override. The retail `player.json` configures saturation, exhaustion and costs for actions including sprinting. It supplies no hunger component with a documented player `max` override. Changing sprint exhaustion changes the cost of an action. Eligibility is a separate behavior. [Retail player definition][playerjson] · [Exhaustion values][exhaustion] · [Retail HUD definition][hudjson]
- **Workaround with gameplay changes.** Clamping native current hunger to a logical cap can leave empty vanilla slots and can prevent sprinting even when the custom meter reads full. Test the native sprint-start and sprint-stop thresholds against an unmodified world, and check eating at the cap, saturation, regeneration, starvation and respawn. A separately displayed hunger value can preserve vanilla behavior by leaving native hunger alone, but then it represents a separate rule rather than the engine's food limit. Decide whether late-life sprint loss is acceptable after measuring the retail behavior. [Hunger component][hunger] · [Entity API][entity] · [Retail HUD definition][hudjson]

## 3. Life state, death and elimination

- **Documented.** Subscribe to `world.afterEvents.entityDie` and filter `EntityDieAfterEvent.deadEntity.typeId === 'minecraft:player'`. `Entity.id` is opaque, is intended to remain consistent across loads of one world and can be read from an invalid entity. `world.afterEvents.playerSpawn` supplies `player` and `initialSpawn`, which indicates first spawn after joining and can be true on reconnect. Use it to restore state, never as the death counter or the sole signal for initialization. [EntityDieAfterEvent][die] · [PlayerSpawnAfterEvent][spawn] · [Entity identity][entity] · [World after events][after]
- **Prototype.** Use one versioned world dynamic property record per opaque `Entity.id`. `world.getDynamicProperty(...)` and `world.setDynamicProperty(...)` let the death handler persist state without mutating the dead player object. Store a life balance and a spawn/death sequence to make each transition idempotent. Reconcile on every spawn and before recovery, and keep the behavior pack header UUID stable across updates. Verify the identity across death, rejoin and world reopen, and exercise a disconnect between death and respawn. World saves and inventory changes have no documented common transaction. Test interrupted writes and distinguish graceful-save guarantees from crash behavior. [World dynamic properties][world] · [Multiplayer scripting][multiplayer] · [Pack identity][manifest]
- **Elimination.** Persist zero lives at death. On the next usable player spawn set `player.setGameMode(GameMode.Spectator)` and reapply to eliminated players when they rejoin. The documented spectator rules prevent normal item use and block or mob interaction. Verify the transition has no playable window and the other participant continues in Survival. This definition preserves vanilla respawn and allows observation. [Player API][player] · [GameMode][gamemode]
- **Adjustable presets.** A world-level record can store the active preset and all four preset values. Register commands for selection and edits with `system.beforeEvents.startup`, `StartupEvent.customCommandRegistry.registerEnum(...)` and `registerCommand(...)`, using `CommandPermissionLevel.Host`. Defer world changes with `system.run(...)` from the command callback. Test actual host permissions and cheats-off behavior with `cheatsRequired: false`. The stable API includes `World.getPackSettings()` since `2.8.0`, while the authoring reference still labels manifest v3 settings experimental. Use the format 2 command path for the prototype. [Custom command registry][commands] · [Scripting custom commands][commands-guide] · [API changelog][changelog] · [Pack manifest][manifest]

## 4. Crafting and full/half recovery

- **Documented.** A `minecraft:recipe_shaped` recipe tagged `crafting_table` fits all nine ingredients. Use prototype rows `DDD`, `NHN`, `DDD` with `minecraft:diamond`, `minecraft:netherite_ingot`, and `minecraft:heart_of_the_sea`. Set a namespaced output with count `1`. Use recipe `format_version` `1.21.20`, which Microsoft uses for a namespaced shaped recipe. Use a diamond as the prototype `unlock` ingredient and verify discovery in Survival. Test a proposed `minecraft:recipe_shapeless` split of one full Artificial Heart into two half items. [Shaped recipe reference][recipe] · [Shapeless recipe reference][split-recipe] · [Microsoft custom recipe sample][recipe-sample]
- **Prototype.** Use distinct full and half item identifiers. Test `world.beforeEvents.itemUse` with a usable item and `ItemUseBeforeEvent.cancel` for vanilla consumption, or test `ItemCustomComponent.onUse` registered by `StartupEvent.itemComponentRegistry.registerCustomComponent(...)` with script-controlled consumption. Choose one activation path after testing controller use. Defer writes out of the before event. Validate eligibility and the actual stack immediately before decrementing it with `EntityInventoryComponent.container` and `Container.setItem(...)`. A use-after or consume callback alone cannot prevent vanilla consumption. Verify zero consumption on rejected use, one item and one grant on valid use, plus behavior when the player dies, leaves or swaps slots during processing. [Item use before event][use] · [Item component registry][item-reg] · [Item custom component][item-custom] · [Inventory][inventory] · [Container][container]
- **Prototype rules requiring product confirmation.** Start with 10 lives as well as 10 hearts and 10 hunger icons. Represent all three linked quantities as integer half units. Death removes two units down to zero, full recovery restores two and half recovery restores one. Treat death losses as lasting until crafted recovery, and treat eliminated players as ineligible. Reject a full item when only one half unit is missing. If recovery is intended to restore lives alone, keep the stat caps separate and revise the restoration cases. Difficulty fixture values are defined in the test plan.

## 5. Windows host and PS5 guest

Microsoft documents cross-platform worlds across Windows and consoles, custom scripts in ordinary behavior packs, and server-side script execution on the multiplayer host. `.mcaddon` is a documented container. The proposed route imports the add-on on Windows, activates both packs in a private multiplayer world, and has the PS5 join through the standard friends flow. [Bedrock platform overview][platform] · [Scripting introduction][scripting] · [Multiplayer scripting][multiplayer] · [File extensions][extensions]

The retail UI includes PlayStation Network settings for normal worlds, a resource download prompt for world add-ons, and a statement that active behavior packs apply to all players. It also provides an error for content barred from cross-platform sessions. That supports testing the friend-world route. A physical PS5 must verify that this private pack joins and downloads, renders correctly, accepts controller use, and preserves each player's progress and elimination on rejoin. [PlayStation world settings][ps-world] · [Resource download prompt][pack-download] · [Behavior pack scope][pack-scope] · [Cross-platform content error][pack-errors]

The next coding session should use a disposable pack to probe the two native caps and HUDs first, then join that world from PS5 with one visible custom item and a host-side event trace. If either cap probe fails, agree on the supported survival rules and display before building the full life loop. [Prototype test plan](hearts-prototype-test-plan.md)
