# Hearts & Lives prototype test plan

All cases are planned. No Minecraft tests have been run. [Hearts & Lives feasibility](hearts-feasibility.md)

## Setup and order

1. Record the exact retail game version on Windows and on a stock PS5, pack versions and UUIDs, script dependency (`@minecraft/server` `2.11.0`), and the state of each experiment toggle. Use Minecraft for Windows as the interactive host. Use two separate signed-in players with online multiplayer allowed and the PS5 account enabled for online play. Keep the guest a normal member.
2. Create an unmodified Survival world as the control and a separate host world for the pack. Use Normal world difficulty for comparison unless a case specifies otherwise. Import one `.mcaddon` on Windows and enable its behavior and resource packs. Require the world resource pack for guests. Start with experiments all off and test the ordinary Survival flow with cheats off. Use an instrumented copy for controlled damage, hunger and fault cases, and record any fixture permissions.
3. Run **P1**, **H1** and **F1** on Windows, and **P2** on PS5 as soon as the pack has one visible custom item. Start with read-only telemetry. Use test fixtures to request the listed caps directly, before implementing life transitions. If probing an entity definition or effect, isolate it in a copy so that the control and workaround results stay attributable. Stop the exact-design track when a native gate fails. Continue life-loop or fallback probes only against clearly identified prototype criteria.
4. Run the life-loop, crafting, preset and fault cases on Windows. Then run **P3** with PS5 hardware. Rerun native candidates and any approved fallback on both clients. Use keyboard and mouse on Windows and the standard PS5 controller.

Record the case ID, build and pack revisions, player alias, tick and event order, current and effective max health and hunger, and the life balance in half units. For food tests also record saturation, exhaustion and `isSprinting`. Capture HUD and join screenshots, the Windows content log, and exact before/after recipe counts. Mark each case Pass, Fail, Blocked or Not run with the evidence and observed result.

## Prototype fixtures

- One heart or hunger icon uses two engine points. For the life-loop tests use `L` for the remaining balance in half lives. `L = 20` on first join. Death subtracts `2` down to `0`, full recovery adds `2`, and half recovery adds `1`. The proposed linked limits for an active player are both `L` engine points. For example, first death yields `L = 18` and nine icons of capacity in each native meter. Half recovery yields `L = 19` and 9½ icons of capacity. These are fixture rules pending confirmation about starting lives and which stats recovery restores.
- When the available deficit is smaller than the item value, reject the entire use and leave inventory intact. Zero lives is terminal. Elimination means permanent Spectator for the normal participant on that world save. Keep the other participant in Survival.
- Use four selectable presets with provisional recovery cooldowns of **0, 100, 200 and 400 gameplay ticks**. Allow the host to edit each value from **0 to 1,200 ticks** in whole ticks. Start a cooldown only on successful recovery. A preset edit affects subsequent successful uses and leaves any already-started cooldown on its original schedule. Persist the selected preset and all edits. The values and cooldown setting are fixtures, pending difficulty design.

## Acceptance cases

### Stable load and platform

| ID | Exercise | Pass criteria |
| --- | --- | --- |
| P1 | Import, activate and open the add-on on Windows. Close and reopen the world. | Both packs are active. The script logs one startup marker per world load, the test item uses its custom icon and name, and the content log has zero add-on errors. Beta APIs and all other experiments are off. |
| P2 | From PS5, first join the unmodified Windows friend world, then join the pack world through the same normal friends or invite flow. Use an account/client without a preinstalled copy of the pack and accept the required download if prompted. | Both joins succeed in a standard Windows-hosted world. PS5 sees the exact custom icon and name, and a controller use produces one host event identifying the correct guest. Retain screenshots and the host log. This case uses no console sideload, Realm, dedicated server or Marketplace installation. |
| P3 | On those same devices, exercise **D1–D3** and **R1–R2** with the PS5 guest and both participants online. Have the guest leave and rejoin, then close and reopen the world on Windows and have the guest rejoin again. | PS5 can craft and use both items with the controller. The host and guest see their own state and expected presentation. Changes to either player leave the other player's balance, caps, inventory and mode unchanged. A zero-life guest remains a non-interacting spectator after both rejoins. Any native caps being claimed also meet **H1** and **F1** on both clients. |

### Native caps and gameplay

| ID | Exercise | Pass criteria |
| --- | --- | --- |
| H1 | Read native health at `L = 20`, `18`, and `19` while fully healed and without effects. Use ordinary damage, then refill. Repeat after respawn and save/reopen. | `EntityHealthComponent.effectiveMax` reads `20`, `18`, and `19` respectively, with a fully healed `currentValue` equal to the measured cap. The vanilla HUD shows capacity for 10, 9, and 9½ hearts, including the capacity of the final slot at `19`. A lost maximum cannot appear as an extra empty slot. Refilling cannot exceed the native cap. |
| H2 | At a reduced limit, test natural healing, direct healing, Regeneration, deliberate Health Boost and Absorption, damage immediately after a heal, and a Totem of Undying. Compare with the control world and capture event order. | Ordinary heals never produce survivable health above the base cap. Effects are tracked distinctly from base capacity and leave the intended base cap after expiry or removal. A totem save keeps the life balance. The next real death costs exactly one life. Any over-cap damage advantage or uncaught exception fails a cap claim. |
| F1 | Read native hunger at `L = 20`, `18`, `19`, and `2` while fed. Deplete and refill through actual food, then repeat after respawn and save/reopen. Include one high-saturation food. | `EntityHungerComponent.effectiveMax` reads `20`, `18`, `19`, and `2`. The vanilla HUD shows capacity for 10, 9, 9½, and 1 icons respectively, with no lost capacity shown as empty slots. Eating cannot raise current hunger above the effective maximum. At full hunger normal food eligibility matches the unmodified game's behavior at full hunger. A display-only change or a current-value clamp cannot pass this case. |
| F2 | In the control, measure sprint entry and continuation separately by controlling hunger in one-point steps from 20 to 0. On flat ground use the same movement input and game mode in both worlds. Repeat around the measured cutoffs in the packed world and at a fully fed `L = 2`. Also test sprint-jumping, exhaustion, eating, natural healing, starvation at zero, and one Peaceful refill case. | Record start and stop cutoffs on keyboard and controller as observed food-point values. For a claim of retained vanilla behavior, the packed world matches the control at the same reachable native hunger, saturation and difficulty, including the measured sprint transition. Identify any progression state in which the cap makes the cutoffs unreachable or prevents natural healing. If full low-cap players cannot sprint, record that as a product decision before approving a fallback or a release. |
| F3 | If a fallback is assessed, run reduced health/hunger, damage, food and respawn cases with the separate presentation enabled. | The fallback reports current and configured maximum values accurately within one second, labels any logical measure separately from the engine meter, and stays legible on Windows and PS5. Record all timing, food, healing and sprint differences from **H1–F2**. A fallback result cannot satisfy either native gate. |

### Death, state and elimination

| ID | Exercise | Pass criteria |
| --- | --- | --- |
| D1 | Start A and B fresh. Kill only A once. Respawn A, exit and rejoin A, then save and reopen. Test mob or player damage, fall, lava, and the void or `/kill` in instrumented copies. Include a non-player death. | Both begin at `L = 20` with 10 hearts and 10 hunger icons. Each confirmed player death produces one decrement of `2`, attributed to the correct opaque ID. Death, respawn and initial spawn on reconnect do not double-charge. Non-player death changes neither balance. A preserves the reduced balance through reconnect and reopen. B stays at `20` until B dies. |
| D2 | Disconnect while on the death screen. Rejoin, respawn, move through a portal, and reopen after a graceful save. Repeat with both players dying close together. Re-import a version-bumped copy with the same behavior pack header UUID and check an unrelated fresh world. | Prior loss is already persisted when the player returns. Each participant is charged once and retains their own record through the pack upgrade. A dimension change makes no new record, and an unrelated world initializes to `20`. There are no invalid-entity errors in the host log. |
| D3 | From `L = 20`, die ten times without recovery. Separately test a death at `L = 1`. In Spectator, try item use, pickup, crafting, block edits, attacks, and another recovery. Rejoin and reopen. | After the ninth death the first player has `L = 2` and remains in Survival. The final death, including the `L = 1` case, clamps to `0`. At the first actionable moment after respawn the eliminated player is in Spectator and cannot perform the listed survival actions. Zero and Spectator survive reload and rejoin. The other participant remains playable. |

### Crafting, recovery and presets

| ID | Exercise | Pass criteria |
| --- | --- | --- |
| R1 | In Survival, pick up a diamond to unlock the recipe, then manually craft the full item on a crafting table with `DDD` / `NHN` / `DDD`. Try recipe-book crafting, the 2×2 grid, and substitute or remove each ingredient type in turn. Use the proposed split recipe. | One full craft consumes exactly 6 diamonds, 2 netherite ingots and 1 Heart of the Sea for one full item. Recipe-book discovery and crafting work after the diamond pickup. The incomplete and substituted layouts produce no full item. Splitting consumes one full item for exactly two half items. |
| R2 | At `L = 16`, use one full item then one half item on the same player at valid cooldown intervals. At `L = 19`, try a full item and then a half item. At `L = 20`, try both. Inspect inventory and state after each use. | The first two accepted uses advance `16 → 18 → 19`, consuming one item each and updating only that player. The full item at `19` is rejected and kept. The half item advances `19 → 20`. Both uses at `20` are rejected and kept. No balance exceeds `20`. The linked limits follow the state, with native behavior subject to **H1** and **F1**. |
| R3 | Use a stack and a last item. Rapidly press and hold use, swap or drop the held item during processing, and exercise recovery while dying or disconnecting. Test a controlled failure between item debit and state update on a copy, then reopen. | Every accepted use matches one debit and its exact grant. Rejected or stale requests change neither inventory nor state. The same request cannot grant twice. Graceful save/reopen preserves the pair. A forced interruption must recover the pair or be logged as a crash-consistency failure, with no claim of crash-safe recovery while the failure is open. |
| C1 | As host, select and edit each of the four presets in the cheats-off world. Try an out-of-range edit, and try both commands as a non-operator guest. With enough deficit, attempt consecutive uses before and at the boundary. Edit a preset during an active cooldown, then reopen. | The host can select each preset and edit its independent value. The guest and invalid input change no setting. For each positive cooldown `N`, the next use is rejected at `N−1` ticks and accepted at `N` if otherwise eligible. At `0`, successive distinct uses incur no preset delay. An in-flight cooldown retains its issued duration. Selection and edits persist. Ingredient counts, starting balance and death loss stay fixed. |

## Release gates and technical risks

| Risk | Evidence required to close it |
| --- | --- |
| **Native maxima and slots (blocking).** A lower current value, hidden bars, or a scripted display can appear correct while the engine still uses its vanilla caps. A replacement `player.json` may conflict with other packs or change with the retail version. | **H1** and **F1** pass on both retail clients with reproducible support for the mechanism. A single-build result from an undocumented override warrants further support and regression review. Otherwise the exact design stays blocked pending a requirement change. |
| **Food and damage semantics (high).** Late caps can disable sprint or natural healing. Scripted heal correction may race damage. | **H2** and **F2** characterize the behavior and the intended survival rules are explicitly accepted. |
| **PS5 delivery and input (blocking).** Ordinary cross-play can work while an individual pack or its resource delivery fails. | **P2** and **P3** pass on physical PS5 hardware with the Windows peer host and the actual packaged files. |
| **Persistence and recovery accounting (high).** Death and spawn can be separated by disconnects, and inventory and world state can save separately. | **D1–D3** and **R2–R3** verify normal-save behavior and isolation, with any interruption limitations recorded. |
| **Undocumented prerequisites (high).** A callback or a configuration route can appear available in declarations while requiring a different setup in game. | **P1**, **R1–R2**, and **C1** pass with all experiments off, with a documented stable activation and configuration path. |

Approve the exact design only after both native gates, ordinary Windows-to-PS5 delivery, and the life loop pass. A separate-display or life-only design needs explicit agreement on the changed behavior and its own PS5 acceptance results.
